01 Scope for This Cycle

This plan covers everything funded by the current quotation — the prediction backbone, source attribution, and the start of the geospatial affected-zone loop. Later phases are named so nothing gets quietly folded in mid-cycle.

In scope — Phase 1–3
  • Random Forest / XGBoost / LightGBM forecasting models (24h, 7-day, 30-day)
  • SHAP-based source attribution for SourceAnalysis
  • PostGIS + geocoding for incident → coordinates
  • Wind-informed affected-zone polygon generation
  • Before/after AQI comparison logging (outcome verification MVP)
Deferred — Phase 4–6
  • Live CPCB/SAMEER/PRANA data integration (pending institutional access)
  • LSTM / deep-learning forecasting (needs live data volume)
  • Anomaly detection for DataProvenance & CommunityFeed
  • Satellite (Sentinel-5P / NASA FIRMS) & CNN spatial modeling
  • Claude Max 20x upgrade, multi-contributor workflow

02 Week-by-Week Timeline

Three build months, each closing with a working demo and a short written review — so scope drift shows up before it costs a month, not after.

Month 1 — Core Prediction Backbone
Weeks 1–4 · Phase 1
W1Setup
Environment & data scaffolding
Stand up the Python/FastAPI microservice, connect Claude Max + Claude Code to the existing TypeScript repo, wire IMD/Open-Meteo meteorological feeds, and confirm the data model swap-in points already flagged as "drop-in replaceable."
Tools: Python, FastAPI, Claude Code, IMD/Open-Meteo API
W2Baseline
30-day AQI trend + inversion-risk models
Train Random Forest baselines for the 30-day AQI trend and the meteorological inversion-risk classifier — the most-validated method family in the underlying literature review.
Tools: scikit-learn, pandas, NumPy
W3Forecast
24-hour forecast model + component wiring
Build the LightGBM/XGBoost 24-hour multivariate forecast and connect model output to CityDetail and Dashboard via the FastAPI endpoint, replacing mock arrays without touching frontend components.
Tools: LightGBM, XGBoost, Express.js bridge
W4Review
Validation, AlertsManager hookup, Month-1 demo
Backtest forecasts against held-out data, feed AlertsManager from real forecast output instead of a static threshold, and run a short internal demo/review before moving into Phase 2.
Deliverable: Working forecast API, demo notes
Month 2 — Source Attribution Layer
Weeks 5–8 · Phase 2
W5SHAP
SHAP integration on the Phase 1 model
Add SHAP on top of the existing XGBoost/CatBoost model — no new model family, just an interpretability layer, per the build-in-order sequencing from the ML method review.
Tools: SHAP, XGBoost/CatBoost
W6Attribution
Real per-category attribution in SourceAnalysis
Replace SourceAnalysis's static mock percentages with live SHAP-driven attribution across road dust, construction, vehicular, and solid-fuel categories.
Tools: SHAP, SourceAnalysis component
W7Validate
Cross-check against CPCB/TERI source data
Validate attribution output against CPCB's and TERI's Pune source-apportionment studies; use Claude for a plain-language explainability pass so output reads clearly to a non-technical nodal officer.
Tools: CPCB/TERI reports, Claude (review)
W8Review
Documentation + Month-2 demo
Document Phase 1–2 output for the eventual government-facing submission, and run the second monthly demo/review before starting the geospatial layer.
Deliverable: SourceAnalysis live, doc pack
Month 3 — Geospatial Loop Begins
Weeks 9–12 · Phase 3 (start)
W9Geo setup
PostGIS + geocoding pipeline
Set up PostgreSQL + PostGIS for spatial storage, prototype affected-zone geometry in QGIS, and wire a reported incident's address/pin to coordinates via Google Maps/Mapbox free tier.
Tools: PostGIS, QGIS, Maps/Mapbox (free tier)
W10Zone logic
Wind-informed affected-zone polygon
Generate a wind-adjusted affected-zone shape (not a static radius) using the meteorological feed from Phase 1, and render it on InteractiveMap.
Tools: PostGIS, wind API, InteractiveMap
W11Outcome
Before/after AQI comparison logging
Build the MVP of AirSense's core differentiator — logging AQI before and after a recommended intervention, so "did it actually work" becomes a stored, checkable fact instead of an example.
Tools: PostGIS, FastAPI
W12Close-out
Integration testing, report, Phase 4–5 ask
Run an end-to-end test (incident → source → zone → intervention → measured outcome), submit the financial closure report to the Principal, and prepare the Phase 4–5 follow-on funding request.
Deliverable: End-to-end demo, financial report

05 Risks & Contingency

Data-access delay MEDIUM
CPCB/PRANA institutional approval takes longer than 3 months.
Mitigation: Phase 1–3 is scoped to run entirely on IMD/Open-Meteo + mock-to-synthetic incident data, so this delay does not block the current cycle — only Phase 4.
Single-developer bandwidth MEDIUM
Solo-founder build across ML, backend, and geospatial work in parallel with coursework.
Mitigation: Claude Max functions as a second engineer for scaffolding, debugging, and documentation — the reason this plan requests Max over Pro for this cycle.
Maps/geocoding usage spike LOW
Google Maps/Mapbox usage exceeds free-tier allowance during Phase 3 testing.
Mitigation: Pilot-scale Pune traffic sits well inside free tiers (Section 4 of the quotation); the Rs. 1,000 reserve covers a short-term overage if needed.
Scope creep into Phase 4–6 HIGH
Temptation to start live-data/LSTM/satellite work before the Phase 1–3 backbone is validated.
Mitigation: Section 1's "deferred" list is explicit and reviewed at each month's close-out demo — nothing moves into scope without a new funding ask.
EXIT CHECKLIST — BEFORE REQUESTING PHASE 4–5 FUNDING
  • 24h / 7-day / 30-day forecast models live and validated
  • SourceAnalysis running on real SHAP attribution, not mock data
  • Affected-zone polygon rendering correctly on InteractiveMap
  • At least one incident logged end-to-end with before/after AQI
  • Financial report submitted to Principal, Rs. 40,300 accounted for
  • CPCB/PRANA access request status confirmed (approved or still pending)
